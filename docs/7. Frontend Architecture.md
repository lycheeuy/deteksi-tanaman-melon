# 1. FILOSOFI ARSITEKTUR FRONTEND

Frontend disusun dengan filosofi **feature-first, bukan type-first** — file dikelompokkan berdasarkan domain fitur (Detection, History, Monitoring) terlebih dahulu, baru di dalamnya dipecah berdasarkan jenis file (component, hook, type). Pendekatan ini dipilih karena setiap fitur pada sistem ini relatif independen (History tidak perlu tahu detail internal Monitoring), sehingga developer dapat fokus pada satu folder fitur tanpa harus melompat ke banyak folder generik tersebar.

| Layer | Tanggung Jawab |
|---|---|
| **Presentation Layer** (`app/`) | Routing & komposisi halaman — merangkai Feature Layer dan Shared Component menjadi halaman utuh, sangat tipis, tanpa business logic |
| **Feature Layer** (`features/`) | Logic spesifik domain: component yang hanya relevan untuk satu fitur, hook yang mengelola data fitur tersebut, type spesifik fitur |
| **Shared Component** (`components/`) | UI murni tanpa pengetahuan domain (Button, Card, Table) — dapat dipakai fitur manapun tanpa modifikasi |
| **API Client** (`services/`) | Satu-satunya lapisan yang mengetahui detail HTTP ke backend FastAPI — Feature Layer tidak pernah memanggil Axios langsung |
| **Utilities** (`utils/`, `lib/`) | Fungsi murni tanpa state React (formatter, validator, helper) |
| **Type Definition** (`types/`) | Kontrak data lintas layer — memastikan struktur response API (04_API.md) konsisten dipakai di seluruh komponen |

**Prinsip dependency:** `app/` → `features/` → `components/` (shared). Shared Component tidak boleh mengimpor apapun dari `features/`, mencegah ketergantungan melingkar dan menjaga komponen UI tetap benar-benar reusable.

# 3. APP ROUTER

| Route | Deskripsi | Alasan Struktur |
|---|---|---|
| `/login` | Halaman login | Dikelompokkan dalam route group `(auth)` agar memakai Authentication Layout terpisah dari dashboard, tanpa memengaruhi struktur URL (`(auth)` tidak muncul di path) |

| `/history/[id]` | Detail satu riwayat | Dynamic route — `id` dipakai langsung untuk memanggil `GET /history/{id}` |
| `/monitoring` | Status kesehatan sistem | Terpisah dari dashboard agar dapat memiliki interval polling sendiri (lebih jarang, sesuai 05_UI_UX.md) |
| `/statistics` | Halaman grafik & statistik | Memuat library chart yang cukup berat — dipisah sebagai route sendiri agar dapat di-*code split* (lihat Bagian 15), tidak membebani initial load dashboard |

**Catatan:** `/` (root) akan melakukan redirect otomatis — ke `/login` jika belum terautentikasi, atau ke `/dashboard` jika sudah (logic ditangani di `app/page.tsx` atau middleware Next.js, dijelaskan lebih lanjut pada implementasi).

# 8. API CLIENT

### 8.1 Struktur
- **Base URL**: `NEXT_PUBLIC_API_BASE_URL` (dibaca dari `config/env.ts`), default mengarah ke `https://<domain-vps>/api/v1` — selaras 04_API.md.
- **Request Interceptor**: menyisipkan header `Authorization: Bearer <token>` secara otomatis ke setiap request (kecuali endpoint `/login`), token diambil dari penyimpanan yang dikelola `AuthContext` (lihat Bagian 16 untuk strategi penyimpanan).
- **Response Interceptor**: 
  - Jika response sukses, langsung mengembalikan `data` dari struktur standar `{ success, message, data }` agar pemanggil tidak perlu unwrap berulang.
  - Jika response gagal (`success: false`) atau status non-2xx, melempar error terstruktur (`{ code, message }`) yang dapat ditangkap seragam oleh hook pemanggil.
  - Status `401` secara khusus memicu logout otomatis + redirect ke `/login` (token sudah tidak valid, mencegah pengguna terjebak di halaman yang terus gagal fetch).
- **Timeout**: default 10 detik untuk endpoint umum; endpoint `/upload` dan `/predict` menggunakan timeout lebih panjang (mis. 30 detik), mengantisipasi waktu inferensi AI yang lebih lama dari request CRUD biasa.
- **API Service Layer** (`services/*Api.ts`): satu file per domain (selaras Service Layer backend di 06_Backend_Blueprint.md), masing-masing mengekspos fungsi bertipe jelas (mis. `getHistoryList(params)`, `getDetectionDetail(id)`) — Feature Layer memanggil fungsi ini, tidak pernah memanggil `apiClient.get(...)` langsung.

### 8.2 Alasan Pemisahan Service Layer di Frontend
Sama seperti alasan Repository Pattern di backend (06_Backend_Blueprint.md Bagian 7): jika struktur endpoint berubah (mis. versi `/api/v2/`), perubahan cukup dilakukan di `services/`, tidak menyebar ke seluruh komponen yang memakainya.

# 9. STATE MANAGEMENT

| Aspek | React Context | Zustand |
|---|---|---|
| Cocok untuk | State global yang jarang berubah & dibutuhkan luas (auth, theme) | State yang sering berubah / butuh akses granular tanpa re-render berlebihan |
| Performa pada state sering berubah | Berisiko re-render berlebihan ke seluruh consumer jika tidak di-split hati-hati | Subscription granular per-slice, lebih efisien |
| Boilerplate | Lebih verbose untuk state kompleks (perlu reducer/provider manual) | Minimal, API langsung berupa hook |
| Kebutuhan testing terpisah | Perlu wrapping Provider di setiap test | Store dapat diuji independen dari komponen React |

### Rekomendasi Final
**Kombinasi keduanya, dengan pembagian tanggung jawab jelas:**
- **React Context** digunakan **khusus** untuk `AuthContext` (data user login & token) — sifatnya benar-benar global, jarang berubah dalam satu sesi, dan secara alami cocok dengan pola Provider yang sudah disiapkan di `app/layout.tsx`.
- **Zustand** digunakan untuk state UI lintas-komponen yang lebih dinamis namun tidak perlu disinkronkan ke server, contoh: state Toast global, state filter History yang ingin dipertahankan saat berpindah tab, atau state UI sidebar (collapsed/expanded).
- **Data dari server** (history, statistics, status) **sengaja tidak disimpan sebagai global state Context/Zustand** — dikelola melalui hook fetching per-fitur (Bagian 12) yang menangani loading/error/refetch sendiri. Ini mencegah state server menjadi "basi" karena tersimpan ganda, dan selaras pendekatan "server state vs client state" yang menjadi best practice umum di ekosistem React modern.

Alasan tidak memilih Zustand untuk seluruhnya: AuthContext berinteraksi erat dengan Next.js App Router (mis. middleware-level check), di mana pola Context+Provider lebih idiomatik untuk Next.js dibanding store eksternal untuk kasus spesifik ini.

# 10. FORM MANAGEMENT

**React Hook Form + Zod** digunakan untuk seluruh form (Login, Filter History, Filter Report).

Alasan:
1. **Performa** — React Hook Form meminimalkan re-render dengan pendekatan uncontrolled input, penting untuk form filter History yang mungkin memiliki banyak field sekaligus.
2. **Validasi terpusat & type-safe** — skema Zod (`lib/zodSchemas.ts`) mendefinisikan aturan validasi sekali (mis. `username` minimal 3 karakter, `date_from` ≤ `date_to`) dan otomatis menghasilkan TypeScript type via `z.infer`, sehingga validasi runtime dan tipe statis selalu sinkron — tidak ada definisi ganda yang bisa saling tidak konsisten.
3. **Validasi konsisten dengan backend** — aturan pada Zod schema dirancang mencerminkan persis aturan validasi 04_API.md (Bagian 9), memberi feedback instan ke pengguna sebelum request dikirim, mengurangi round-trip ke server untuk kesalahan input sederhana.
4. **Integrasi alami dengan komponen UI generik** — `react-hook-form` menyediakan `Controller` untuk menghubungkan komponen custom (mis. date range picker) tanpa kehilangan keuntungan validasi.

# 11. TYPE SYSTEM

| Kategori | Lokasi | Fungsi |
|---|---|---|
| **DTO** (Data Transfer Object) | `types/api/` | Representasi *persis* bentuk JSON yang dikirim/diterima backend (mis. `DetectionHistoryDTO` mengikuti field response `/history` apa adanya) |
| **API Response** | `types/api/` | Wrapper generik `ApiResponse<T>` dan `PaginatedResponse<T>` yang mencerminkan struktur standar 04_API.md (`success`, `message`, `data`, `pagination`) |
| **Entity** | `types/entities/` | Representasi domain yang sudah "dibersihkan"/diolah untuk kebutuhan UI (mis. `DetectionEntity` dengan field tambahan hasil turunan seperti `statusColor` yang tidak ada di response API mentah) — memisahkan DTO dari Entity mencegah perubahan kecil pada API langsung merembet ke seluruh komponen UI |
| **Form Type** | `types/forms/` | Diturunkan dari Zod schema (`z.infer<typeof schema>`), dipakai langsung oleh `react-hook-form` |
| **Utility Type** | `types/` (root) | Tipe generik lintas domain, mis. `Nullable<T>`, `PaginationParams`, `SortOrder` |

**Alur konversi data:** Response mentah dari `services/` bertipe DTO → dipetakan (mapping function di `features/<fitur>/hooks/`) menjadi Entity → dikonsumsi komponen. Pemetaan ini juga titik yang tepat untuk menerjemahkan label/status (sesuai `constants/labels.ts`) menjadi representasi siap-tampil (nama Indonesia, warna badge).

# 12. HOOKS

| Hook | Fungsi |
|---|---|
| `useAuth` | Mengelola login, logout, status autentikasi, dan data user aktif (mengonsumsi `AuthContext`) |
| `useDetection` | Mengelola fetching `/latest` dengan polling interval, serta submit `/predict` (upload manual) |
| `useHistory` | Mengelola fetching `/history` dengan parameter filter/sort/search/pagination terkini, termasuk fungsi delete (admin) |
| `useHistoryDetail` | Fetching `/history/{id}` |
| `useMonitoring` | Polling `/status` dengan interval lebih jarang dibanding `useDetection` |
| `useStatistics` | Fetching `/statistics` |
| `useReport` | Mengelola submit filter & trigger download file dari `/download/{format}` |
| `useToast` | Antarmuka memicu notifikasi global (sukses/error/warning), terhubung ke store Zustand Toast |
| `usePagination` | Hook generik (lintas fitur) mengelola state `page`/`limit` dan kalkulasi `total_page`, dipakai bukan hanya History tapi komponen list manapun di masa depan |
| `useDebounce` | Hook generik menunda eksekusi value (dipakai `SearchBar`) agar tidak memicu request berlebihan saat pengguna mengetik |

Hook spesifik fitur (`useDetection`, `useHistory`, dst) ditempatkan di `features/<fitur>/hooks/`, sedangkan hook generik lintas-fitur (`usePagination`, `useDebounce`, `useToast`) ditempatkan di `hooks/` root — selaras prinsip pemisahan Bagian 1.

# 13. STYLING

| Aspek | Pendekatan |
|---|---|
| **Struktur class** | Utility-first murni (Tailwind), tanpa custom CSS kecuali untuk hal yang tidak dapat dicapai utility class (mis. animasi kompleks) |
| **Utility** | Pemakaian langsung utility Tailwind di JSX; kombinasi class panjang yang berulang (>5 class dipakai berulang di banyak tempat) diekstrak menjadi variant via helper `cva` (class-variance-authority) di level komponen `components/ui/`, bukan didefinisikan ulang di tiap pemakaian |
| **Responsive Rule** | Meski target utama desktop, breakpoint Tailwind standar (`md`, `lg`, `xl`) tetap dipasang di level layout dasar sejak awal sebagai pondasi murah untuk Future Scalability "Mobile Version", tanpa effort tambahan saat ini |
| **Design Token** | Seluruh warna pada 05_UI_UX.md Bagian 2.1 didefinisikan sebagai CSS variable di `styles/globals.css` dan dipetakan ke Tailwind theme (`tailwind.config`), bukan hex literal langsung di class — satu sumber kebenaran warna |
| **Dark Mode Ready** | Karena token warna sudah berbasis CSS variable, penambahan dark mode kelak hanya memerlukan satu set nilai variable alternatif (diaktifkan via class `dark` pada `<html>`), tanpa mengubah satupun komponen yang sudah ada |

# 14. ERROR HANDLING

| Jenis Error | Penanganan UI |
|---|---|
| **API Error** (`success: false` dari backend) | Ditangkap di hook fetching, ditampilkan via `Toast` (error) dengan `message` dari response; untuk error form-level (422), pesan dipetakan ke field spesifik via React Hook Form `setError` |
| **Network Error** (request gagal total, tidak ada response) | Pesan generik "Tidak dapat terhubung ke server" + opsi tombol "Coba Lagi", dibedakan dari API Error agar pengguna tahu masalah ada di koneksi, bukan validasi |
| **Empty State** | Komponen `EmptyState` ditampilkan saat data kosong namun fetching berhasil (bukan error) — penting dibedakan dari error agar tidak membingungkan pengguna |
| **Loading** | `loading.tsx` per-route (Suspense) untuk transisi halaman penuh; `LoadingSpinner`/skeleton lokal untuk refetch parsial (mis. saat ganti filter History tanpa reload seluruh halaman) |
| **404** | `not-found.tsx` global, juga dipicu manual di `history/[id]/page.tsx` bila `GET /history/{id}` mengembalikan 404 |
| **500 / Error Tak Terduga** | `error.tsx` per-segment (Next.js Error Boundary) menangkap exception rendering, menampilkan pesan ramah + tombol reset, mencegah seluruh aplikasi blank putih |

# 15. PERFORMANCE

| Strategi | Penerapan |
|---|---|
| **Lazy Loading** | Komponen berat yang tidak langsung terlihat (mis. Modal konfirmasi delete) di-load on-demand via `next/dynamic` |
| **Image Optimization** | `next/image` dipakai untuk seluruh gambar hasil deteksi & logo, memanfaatkan optimasi format/ukuran otomatis — penting karena gambar bounding box akan sering ditampilkan berulang di History (thumbnail) dan Detail |
| **Code Splitting** | Otomatis per-route bawaan Next.js App Router; ditambah `next/dynamic` khusus untuk library chart (Statistics) yang berat, agar tidak terbundel ke halaman lain yang tidak membutuhkannya |
| **Memoization** | `useMemo`/`useCallback` diterapkan selektif pada kalkulasi turunan yang mahal (mis. transformasi data chart) dan pada komponen `Table`/list panjang untuk mencegah re-render baris yang tidak berubah |
| **Dynamic Import** | Sama dengan Code Splitting di atas, khusus dipakai juga untuk komponen yang bergantung pada `window`/browser API (jika ada) agar kompatibel dengan SSR Next.js |
| **Polling efficiency** | Interval polling Live Detection vs Monitoring dibedakan (selaras 05_UI_UX.md) — mencegah request berlebihan yang membebani VPS 1 vCPU |

# 16. SECURITY (FRONTEND)

| Aspek | Praktik |
|---|---|
| **Penyimpanan token** | Access token dari `/login` disimpan di **httpOnly cookie** (di-set melalui Route Handler Next.js yang menjembatani request login ke backend), bukan `localStorage` — mencegah pencurian token via XSS, karena JavaScript di sisi klien tidak dapat membaca httpOnly cookie sama sekali |
| **Validasi input** | Seluruh form memakai Zod schema (Bagian 10) sebagai lapisan pertama sebelum request dikirim — namun validasi ini bersifat *UX improvement*, bukan satu-satunya lapisan keamanan; backend (04_API.md Bagian 9) tetap menjadi sumber validasi yang sebenarnya |
| **Sanitasi data** | Seluruh data dari API dirender melalui binding React standar (bukan `dangerouslySetInnerHTML`), sehingga React secara default sudah melakukan escaping terhadap output yang berpotensi mengandung karakter berbahaya |
| **Penanganan session** | Middleware Next.js (`middleware.ts`, level implementasi) memeriksa keberadaan cookie token untuk melindungi route group `(dashboard)` sebelum halaman dirender di server, mencegah konten dashboard "berkedip" sebelum redirect terjadi (lebih aman & lebih baik UX dibanding pengecekan murni di client-side) |
| **Logout** | Memanggil endpoint `/logout` (invalidasi token di server) **dan** menghapus cookie di sisi klien — bukan hanya salah satu, agar token benar-benar tidak dapat dipakai ulang |

# 17. TESTING

| Jenis Test | Cakupan | Tools (rekomendasi) |
|---|---|---|
| **Component Test** | Komponen `components/ui/` secara terisolasi — memastikan `Badge` merender warna sesuai props, `Pagination` memanggil `onPageChange` dengan nilai benar | React Testing Library + Vitest/Jest |
| **Page Test** | Render halaman dengan data mock (mis. memastikan `EmptyState` muncul saat History kosong, `Loading` muncul saat fetching) | React Testing Library, mock `services/` layer |
| **Integration Test** | Alur lintas-komponen dalam satu fitur, mis. mengisi filter History → memicu fetch ulang → tabel ter-update sesuai data mock | React Testing Library + mock API Client (tidak memanggil backend nyata) |

**Prioritas:** Component Test pada `components/ui/` diprioritaskan tinggi karena dipakai di seluruh aplikasi — bug di sini berdampak luas. Integration Test diprioritaskan pada fitur History (logic filter/pagination paling kompleks) dan Detection (alur upload-predict-tampilkan hasil).

# 18. FUTURE SCALABILITY

| Kebutuhan Masa Depan | Bagaimana Arsitektur Saat Ini Mendukung |
|---|---|
| **Dark Mode** | Design token berbasis CSS variable (Bagian 13) — tinggal menambah satu set nilai alternatif, tanpa mengubah komponen |
