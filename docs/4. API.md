# 1. PENDAHULUAN

### 1.1 Tujuan Dokumen
Dokumen ini mendefinisikan kontrak antarmuka (interface contract) antara Backend FastAPI dengan tiga konsumen utama: ESP32-CAM, Frontend NextJS, dan Administrator/User. Setiap endpoint dirancang agar dapat langsung diterjemahkan menjadi router FastAPI tanpa ambiguitas, sekaligus menjadi acuan dokumentasi Swagger/OpenAPI.

### 1.2 Prinsip Desain
- **Resource-oriented** — URL merepresentasikan resource (`/history`, `/devices`), bukan aksi.
- **Stateless** — autentikasi menggunakan token, server tidak menyimpan session di memori.
- **Predictable** — format response konsisten di seluruh endpoint, memudahkan penanganan error di sisi frontend.
- **Backward-compatible by design** — versioning sejak awal (`/api/v1/`) agar perubahan besar di masa depan tidak merusak klien lama (ESP32 firmware khususnya, yang tidak selalu mudah di-update serentak).

### 1.3 Base URL
```
https://<domain-vps>/api/v1/
```

# 3. AUTHENTICATION API

### 3.1 `POST /api/v1/login`

**Deskripsi:** Autentikasi user/administrator menggunakan username & password, mengembalikan access token.

**Request Body:**
```json
{
  "username": "admin01",
  "password": "string"
}
```

**Validasi:**
- `username`: wajib, string, 3–50 karakter
- `password`: wajib, string, minimal 8 karakter

**Response Sukses (200):**
```json
{
  "success": true,
  "message": "Login berhasil",
  "data": {
    "access_token": "jwt-token-string",
    "token_type": "bearer",
    "expires_in": 3600,
    "user": {
      "id": "uuid",
      "username": "admin01",
      "full_name": "Admin Satu",
      "role": "admin"
    }
  }
}
```

**Response Gagal (401):**
```json
{
  "success": false,
  "message": "Username atau password salah",
  "error": { "code": "INVALID_CREDENTIALS" }
}
```

**Status Code:** `200` sukses, `401` kredensial salah, `422` validasi body gagal.

**Deskripsi:** Mengakhiri sesi aktif (invalidasi token di sisi server, mis. blacklist token).

**Status Code:** `200` sukses, `401` token tidak valid/sudah expired.

# 4. DETECTION API

### 4.1 `POST /api/v1/upload`

**Deskripsi:** Endpoint khusus ESP32-CAM untuk mengirim gambar hasil capture secara periodik. Memicu seluruh pipeline inferensi secara otomatis (preprocessing → inferensi → bounding box → simpan ke database).

**Request:** `multipart/form-data`

| Field | Tipe | Wajib | Keterangan |
|---|---|---|---|
| image | file | Ya | Format jpg/jpeg/png, maksimal 5 MB |
| device_id | string (UUID) | Ya | Identitas perangkat terdaftar |

**Validasi:**
- Ekstensi file harus `.jpg`, `.jpeg`, atau `.png`
- Ukuran file ≤ 5 MB
- `device_id` harus terdaftar di tabel `devices`; jika tidak ditemukan → `404`
- Gambar harus dapat di-decode (bukan file korup) → jika gagal, `400`

**Flow Internal (sesuai Architecture):**
ESP32 → Upload → Backend Validasi → Model AI → Bounding Box → Database → Response JSON

**Response Sukses (201):**
```json
{
  "success": true,
  "message": "Deteksi berhasil diproses",
  "data": {
    "id": "uuid",
    "device_id": "uuid",
    "label": "buah_siap",
    "pruning_status": "siap_pangkas",
    "image_path": "/storage/images/2026/06/30/abc123.jpg",
    "inference_time": 182.4,
    "detection_time": "2026-06-30T10:15:00Z"
  }
}
```

**Response Gagal — Format tidak didukung (400):**
```json
{
  "success": false,
  "message": "Format file tidak didukung",
  "error": { "code": "INVALID_FILE_FORMAT", "allowed": ["jpg", "jpeg", "png"] }
}
```

**Response Gagal — Ukuran melebihi batas (413):**
```json
{
  "success": false,
  "message": "Ukuran file melebihi batas maksimum 5 MB",
  "error": { "code": "FILE_TOO_LARGE", "max_size_mb": 5 }
}
```

**Status Code:** `201` deteksi tersimpan, `400` file korup/format salah, `404` device tidak terdaftar, `413` file terlalu besar, `422` field hilang.

### 4.2 `POST /api/v1/predict`

**Deskripsi:** Digunakan saat User mengunggah gambar secara manual melalui dashboard (mis. untuk pengujian model di luar siklus ESP32). Menjalankan pipeline inferensi yang sama dengan `/upload`, namun **tanpa keterkaitan wajib ke `device_id` fisik** — dapat menggunakan device virtual/manual identifier.

**Header wajib:** `Authorization: Bearer <token>`

**Request:** `multipart/form-data`

| Field | Tipe | Wajib | Keterangan |
|---|---|---|---|
| image | file | Ya | Format jpg/jpeg/png, maksimal 5 MB |

**Response Sukses (200):**
```json
{
  "success": true,
  "message": "Prediksi berhasil",
  "data": {
    "id": "uuid",
    "label": "daun_siap",
    "pruning_status": "siap_pangkas",
    "image_path": "/storage/images/manual/2026/06/30/xyz789.jpg",
    "inference_time": 175.0,
    "detection_time": "2026-06-30T10:20:00Z"
  }
}
```

**Status Code:** `200` sukses, `400` file korup/format salah, `401` belum login, `413` file terlalu besar.

### 4.4 `GET /api/v1/history`

**Deskripsi:** Mengambil daftar riwayat deteksi dengan dukungan pagination, sorting, filtering, dan searching.

**Header wajib:** `Authorization: Bearer <token>`

**Query Parameter:**

| Parameter | Tipe | Default | Keterangan |
|---|---|---|---|
| page | integer | 1 | Halaman data |
| limit | integer | 20 | Jumlah data per halaman (maks 100) |
| sort_by | string | created_at | Kolom pengurutan: `created_at`, `detection_time`, `label` |
| order | string | desc | `asc` atau `desc` |
| label | string | – | Filter berdasarkan label |
| status | string | – | Filter `pruning_status`: `siap_pangkas` / `belum_siap_pangkas` |
| device_id | UUID | – | Filter berdasarkan device |
| date | string (YYYY-MM-DD) | – | Filter tanggal deteksi tertentu |
| date_from / date_to | string (YYYY-MM-DD) | – | Filter rentang tanggal |
| keyword | string | – | Pencarian bebas pada nama file/label |

**Contoh Penggunaan:**
```
GET /api/v1/history?page=2&limit=10&label=buah_siap&status=siap_pangkas&date_from=2026-06-01&date_to=2026-06-30
GET /api/v1/history?keyword=buah&sort_by=detection_time&order=asc
```

**Response Sukses (200):**
```json
{
  "success": true,
  "message": "Berhasil mengambil riwayat deteksi",
  "data": {
    "items": [
      {
        "id": "uuid",
        "device_id": "uuid",
        "label": "buah_siap",
        "pruning_status": "siap_pangkas",
        "image_path": "/storage/images/2026/06/29/img001.jpg",
        "detection_time": "2026-06-29T14:00:00Z"
      }
    ],
    "pagination": {
      "page": 2,
      "limit": 10,
      "total": 156,
      "total_page": 16,
      "current_page": 2,
      "next_page": 3,
      "previous_page": 1

}
```

**Status Code:** `200` sukses, `401` belum login, `422` parameter query tidak valid.

### 4.6 `DELETE /api/v1/history/{id}`

**Deskripsi:** Menghapus satu riwayat deteksi tertentu.

**Strategi: Soft Delete** (menambahkan kolom `deleted_at` pada `detection_history`, bukan menghapus baris secara fisik).

**Alasan:**
1. **Kepentingan penelitian/skripsi** — data deteksi adalah hasil eksperimen yang bernilai bagi analisis penelitian; penghapusan permanen berisiko menghilangkan data yang ternyata masih dibutuhkan untuk evaluasi/laporan.
2. **Audit trail** — setiap penghapusan tetap tercatat di `activity_logs`, namun jejak data asli tetap ada untuk keperluan investigasi jika terjadi kesalahan penghapusan.
3. **Konsistensi referensial** — jika di masa depan ditambahkan fitur seperti notifikasi atau laporan teragregasi yang sudah memuat referensi ke `detection_history.id`, hard delete berisiko menyebabkan broken reference.
4. **Reversibility** — soft delete memungkinkan fitur "restore" ditambahkan di kemudian hari tanpa perubahan struktur tambahan.

Seluruh query `GET /history` dan `GET /latest` secara default mengecualikan baris dengan `deleted_at IS NOT NULL`.

**Header wajib:** `Authorization: Bearer <token>` (role: `admin`)

**Response Sukses (200):**
```json
{
  "success": true,
  "message": "Riwayat deteksi berhasil dihapus",
  "data": { "id": "uuid", "deleted_at": "2026-06-30T11:00:00Z" }
}
```

**Status Code:** `200` sukses, `401` belum login, `403` role tidak memiliki izin, `404` ID tidak ditemukan.

# 7. DOWNLOAD API

### 7.1 `GET /api/v1/download/txt`

**Deskripsi:** Menghasilkan laporan riwayat deteksi dalam format TXT. Struktur endpoint dirancang generik (`/download/{format}`) sehingga penambahan `/download/pdf` dan `/download/xlsx` di masa depan tidak memerlukan perubahan pada endpoint yang sudah ada — hanya menambah handler baru untuk format baru.

**Header wajib:** `Authorization: Bearer <token>`

**Query Parameter (opsional, sama dengan filter `/history`):**

| Parameter | Tipe | Keterangan |
|---|---|---|
| date_from / date_to | string (YYYY-MM-DD) | Rentang tanggal laporan |
| label | string | Filter label |
| status | string | Filter status pangkas |
| device_id | UUID | Filter device |

**Format Isi File TXT:**
```
LAPORAN DETEKSI TANAMAN MELON
Periode: 2026-06-01 s.d. 2026-06-30
Dibuat pada: 2026-06-30 11:15:00

No   Tanggal              Device                 Label              Status              Durasi (ms)
1    2026-06-29 14:00:00  ESP32-Greenhouse-1     Buah Siap          Siap Pangkas        190.2
2    2026-06-29 13:55:00  ESP32-Greenhouse-1     Daun Tidak Siap    Belum Siap Pangkas  178.5
...

Total Data: 156
```

**Response Sukses (200):**
Header response: `Content-Type: text/plain; charset=utf-8`, `Content-Disposition: attachment; filename="laporan-deteksi-20260630.txt"`

**Response Gagal — Tidak ada data pada rentang filter (404):**
```json
{
  "success": false,
  "message": "Tidak ada data untuk rentang filter yang dipilih",
  "error": { "code": "NO_DATA_FOUND" }
}
```

**Status Code:** `200` sukses (file diunduh), `401` belum login, `404` tidak ada data.

# 8. RESPONSE STANDARD

Seluruh endpoint **wajib** mengembalikan struktur berikut.

**Format sukses:**
```json
{
  "success": true,
  "message": "Penjelasan singkat hasil operasi",
  "data": { }
}
```

**Format gagal:**
```json
{
  "success": false,
  "message": "Penjelasan singkat kegagalan",
  "error": {
    "code": "ERROR_CODE_STRING",
    "details": "Informasi tambahan opsional, mis. field mana yang gagal validasi"
  }
}
```

**Struktur `error` object:**

| Field | Tipe | Keterangan |
|---|---|---|
| code | string | Kode error unik, `UPPER_SNAKE_CASE`, dipakai frontend untuk logic penanganan error (bukan parsing teks `message`) |
| details | string / object / array | Opsional — detail teknis (mis. daftar field yang gagal validasi pada `422`) |

# 9. VALIDATION RULES

| Endpoint/Field | Aturan |
|---|---|
| `username` | wajib, 3–50 karakter, alphanumeric + underscore |
| `password` | wajib, minimal 8 karakter |
| `image` (upload/predict) | wajib, ekstensi `.jpg/.jpeg/.png`, maksimal 5 MB, harus dapat di-decode sebagai gambar valid |
| `device_id` | wajib pada `/upload`, harus UUID valid dan terdaftar di tabel `devices` |
| `id` (path param) | harus UUID valid, jika format salah → `422`, jika tidak ditemukan → `404` |
| `page` | integer ≥ 1, default 1 |
| `limit` | integer 1–100, default 20 |
| `label` (query) | harus salah satu dari 5 enum label yang valid |
| `status` (query) | harus `siap_pangkas` atau `belum_siap_pangkas` |
| `date` / `date_from` / `date_to` | format `YYYY-MM-DD`, `date_from` tidak boleh lebih besar dari `date_to` |
| `sort_by` | harus salah satu kolom yang diizinkan (whitelist), mencegah SQL injection melalui parameter sorting |

# 10. HTTP STATUS CODE

| Kode | Kapan Digunakan |
|---|---|
| 200 | Request berhasil diproses (GET, DELETE, POST aksi non-resource-creation seperti `/predict`, `/login`) |
| 201 | Resource baru berhasil dibuat (`POST /upload` — record deteksi baru tersimpan) |
| 400 | Request tidak valid secara semantik (mis. file gambar korup, format tidak sesuai logika bisnis) |
| 401 | Tidak terautentikasi — token tidak ada, tidak valid, atau sudah expired |
| 403 | Terautentikasi tetapi tidak memiliki izin (mis. `user` mencoba mengakses endpoint khusus `admin`) |
| 404 | Resource yang diminta tidak ditemukan (ID tidak ada, endpoint tidak ada) |
| 413 | Ukuran payload/file melebihi batas maksimum (5 MB) |
| 422 | Request gagal validasi schema (field wajib hilang, tipe data salah, format query parameter salah) |
| 500 | Kesalahan internal server (mis. model AI gagal dimuat, koneksi database terputus saat proses) |

# 11. PAGINATION

Diterapkan pada seluruh endpoint yang mengembalikan list data (`/history`).

**Struktur objek `pagination`:**

| Field | Tipe | Keterangan |
|---|---|---|
| page | integer | Halaman saat ini yang diminta |
| limit | integer | Jumlah item per halaman |
| total | integer | Total seluruh data yang cocok dengan filter |
| total_page | integer | Total halaman = `ceil(total / limit)` |
| current_page | integer | Sama dengan `page`, eksplisit untuk kejelasan di sisi frontend |
| next_page | integer / null | Nomor halaman berikutnya, `null` jika sudah di halaman terakhir |
| previous_page | integer / null | Nomor halaman sebelumnya, `null` jika di halaman pertama |

# 12. FILTERING

History dapat difilter berdasarkan kombinasi parameter berikut (dapat digabung, bersifat `AND`):

| Filter | Parameter | Contoh |
|---|---|---|
| Tanggal spesifik | `date` | `?date=2026-06-29` |
| Rentang tanggal | `date_from`, `date_to` | `?date_from=2026-06-01&date_to=2026-06-30` |
| Label | `label` | `?label=buah_siap` |
| Status Pangkas | `status` | `?status=siap_pangkas` |
| Device | `device_id` | `?device_id=<uuid>` |

Filter dapat dikombinasikan, mis: `?label=daun_siap&status=siap_pangkas&device_id=<uuid>`.

---

# 13. SEARCHING

Pencarian dilakukan melalui parameter `keyword` pada `/history`, mencakup pencarian pada:

| Target Pencarian | Mekanisme |
|---|---|
| Label | Pencocokan parsial nama label (mis. `keyword=buah` mencocokkan `buah_siap` dan `buah_tidak_siap`) |
| Nama file gambar | Pencocokan parsial pada `image_path` |
| Tanggal | Jika `keyword` berformat tanggal (`YYYY-MM-DD`), otomatis dicocokkan terhadap `detection_time` |

Pencarian bersifat **case-insensitive** dan digabungkan dengan filter lain menggunakan logika `AND`.

# 14. VERSIONING

**Strategi saat ini:** seluruh endpoint berada di bawah `/api/v1/`.

**Strategi jika muncul `/api/v2/` di masa depan:**
1. `/api/v1/` **tidak langsung dihapus** — tetap berjalan paralel selama periode transisi (mis. minimal hingga firmware ESP32 yang ada di lapangan selesai dimigrasikan), karena perangkat keras tidak selalu dapat di-update serentak seperti aplikasi web.
2. Perubahan **breaking** (mengubah struktur request/response yang sudah ada) wajib masuk ke `/v2/`; perubahan **non-breaking** (menambah field baru bersifat opsional, menambah endpoint baru) cukup ditambahkan ke `/v1/` tanpa versi baru.
3. Routing FastAPI dipisah per versi menggunakan `APIRouter` dengan prefix berbeda, sehingga `v1` dan `v2` dapat hidup berdampingan dalam satu codebase tanpa duplikasi logic inti (service layer tetap sama, hanya schema/response layer yang berbeda jika diperlukan).
4. Dokumentasi Swagger menampilkan kedua versi secara terpisah (mis. `/api/v1/docs` dan `/api/v2/docs`) agar konsumen API tidak tertukar.
5. Endpoint versi lama diberi tenggat *deprecation* yang diumumkan terlebih dahulu (mis. melalui header response `Deprecation: true` dan `Sunset: <date>`) sebelum benar-benar dimatikan.

| GET | `/api/v1/me` | Ya | Data user yang sedang login |
| POST | `/api/v1/upload` | Tidak (device key, bukan user) | Upload gambar dari ESP32-CAM, trigger inferensi otomatis |
| POST | `/api/v1/predict` | Ya | Upload gambar manual oleh user untuk diuji ke model |
| GET | `/api/v1/latest` | Ya | Hasil deteksi paling baru |
| GET | `/api/v1/history` | Ya | Daftar riwayat deteksi (pagination, filter, search) |
| GET | `/api/v1/history/{id}` | Ya | Detail satu riwayat deteksi |
| DELETE | `/api/v1/history/{id}` | Ya (admin) | Soft delete satu riwayat deteksi |
| GET | `/api/v1/status` | Ya | Status kesehatan seluruh komponen sistem |
| GET | `/api/v1/statistics` | Ya | Ringkasan statistik & distribusi label |
| GET | `/api/v1/download/txt` | Ya | Unduh laporan riwayat deteksi format TXT |

> Catatan autentikasi `/upload`: karena dikirim oleh ESP32 (bukan user login), endpoint ini sebaiknya diamankan menggunakan mekanisme terpisah (mis. **device API key** per perangkat, divalidasi terhadap tabel `devices`), bukan Bearer Token user — ESP32 tidak melalui flow `/login`. Detail skema device key dapat diperdalam pada tahap Security Specification berikutnya bila diperlukan.

Setiap endpoint pada implementasi FastAPI nantinya akan dilengkapi:
- `summary` & `description` (untuk Swagger UI)
- `response_model` (Pydantic schema, sesuai struktur `data` pada contoh response di atas)
- `status_code` eksplisit per endpoint
- `tags` pengelompokan: `Authentication`, `Detection`, `Monitoring`, `Statistics`, `Download`
